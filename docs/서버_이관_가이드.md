### 1.2 비동기 어댑터 전환 (ADR-001 예고 절차)

1. `GameService`를 감싸는 `RemoteGameService` 작성: 메서드마다 `Promise<T>` 반환, 오류는 `GameError{code,message,details}` 그대로 직렬화.
2. UI 호출부를 `await`로 바꾼다. 조회는 `useSyncExternalStore` 대신 캐시 스토어(응답 → 스냅샷) + `subscribe`는 서버 푸시(WebSocket/SSE)로.
3. 낙관적 갱신은 하지 않는다(결과는 서버가 정함). 변경 후 서버가 돌려준 스냅샷으로 교체.
4. 오프라인 모드를 남기려면 로컬 서비스와 원격 서비스를 `serviceHost`에서 고르게 둔다(서비스를 만드는 자리: `src/ui/service/serviceHost.ts`의 `createService`).
5. 계약 major(4.0.0): 기기 전용 메서드 제거, 진행 메서드 제거. 1.x 죽은 경로는 3.0.0에서 이미 삭제했다(최종 리뷰 F-m13).

## 3. 일일 마감·동시 킥오프 스케줄러

현재 `advanceDayState(state)` 한 번 = 기획서 3.1의 하루(20:50 마감 → 21:00 시뮬 → 21:15 결과 → 00:00 처리). 서버에서는 이것을 시각별 작업으로 나눈다.

| 시각(KST, Q2) | 작업 | 현재 코드 위치 |
|---|---|---|
| 20:50 | 마감: 제안 만료, `resolvePlan`으로 확정본 고정(동결) | `domain/day/advanceDay.ts` DEADLINE·RESOLVE_PLANS |
| 21:00 | 리그별 경기 시뮬(리그 단위 병렬, 리그 안 `matchId` 순) | SIMULATE·APPLY_RESULTS |
| 21:15 | 결과 공개·푸시. Day 26이면 승강 판정 | SEASON_JUDGEMENT |
| 00:00 | 회복·연봉·성장 틱·이적 창 열림/정산·은퇴·편지 | DAILY_PROCESSING, `transfer/flow.ts` |
| Day 28 → Day 1 | 시즌 경계 | `domain/career/seasonTransition.ts` |

- 멱등: 작업 키 = `(worldId, season, day, step)`. 시즌 경계는 이미 `boundarySeason` 표식이 있다. 재시도해도 같은 결과(시드가 상태에서만 나옴).
- 원자성: 리그 단위 트랜잭션. 한 리그 실패가 다른 리그를 막지 않게 한다.
- 가속 서버(기획서 3.6)는 같은 작업을 짧은 간격으로 돌리면 된다.
- 성능 참고: 하루 처리 p50 약 22ms/70구단(Node, `docs/성능_측정.md`). 엔진 1경기 p95 1.7ms.

## 6. 세이브 스키마 → DB 모델

현재 `GameState` 단일 문서(10시즌 JSON 3.67MB, 구성은 `docs/성능_측정.md` 4장). 서버에선 월드를 여러 사용자가 공유하므로 테이블로 나눈다.

| 테이블 | 현재 필드 | 키 |
|---|---|---|
| worlds | `seed`, `settings`, `boundarySeason` | world_id |
| leagues | `leagues[]` | world, season, league_id |
| clubs | `clubs`, `Club.tactics`·`training`·`lastUsedPlan`·`defaultPlan` | club_id |
| memberships | `memberships` | club_id, user_id |
| players / player_history | `players`(FA 포함), `Player.history` | player_id / player_id, season |
| fixtures / match_summaries / match_records | `fixtures`, `summaries`, `records` | match_id |
| plans | `plans[club]` | club_id, match_id, 상태(DRAFT/CONFIRMED) |
| finances / ledger | `finances`, 원장 | club_id / club_id, seq |
| transfer_windows / listings / bids | `transferMarket` | window_id / listing_id / listing_id, club_id |
| pending_renewals | `pendingRenewals` | player_id |
| inbox | `inbox` | user_id(또는 club_id), id |
| proposals / deal_proposals | `proposals`, `dealProposals` | proposal_id |
| season_outcomes | `seasonHistory`, `pendingOutcome` | league_id, season |
| action_log | `actionLog`(이미 별도 저장소) | append-only |

- 변환: 기존 `migrateSave`(스키마 1→2→3)를 거친 뒤 테이블로 분해. 개인 오프라인 세이브는 **온라인 월드로 들여오지 않는다**(경쟁 공정성). 필요하면 "오프라인 기록 보관"만.
- 보관 규칙 유지: 상세 기록은 현재 + 직전 시즌(D28), 편지 90일(D27).
- 가져오기 검증(`saveProblem`·`membersProblem`)은 서버 입력 검증기의 출발점. `__proto__` 키(F-m12)는 스키마 검증기로 막는다.

## 7. 치트 방지 (서버 권위)

| 위협 | 대책 |
|---|---|
| 세이브 편집·가져오기 | 서버 모드에 `importSave` 없음. 상태는 서버 DB만 원천 |
| 결과 미리 계산 | `gameSeed` 비공개, 마감 후 동결, 시뮬은 서버에서만 |

| 다중 계정·담합 | 기획서 13.2 연관 계정 분산, 6.4 5단계 배치 제약 |
| 요청 폭주 | 사용자별 레이트 리밋, 변경 요청 멱등 키 |
| 클라이언트 변조 | 클라이언트는 표시만. 미리보기(`previewResolvedPlan`·`getMatchupPreview`)도 서버 응답 |
